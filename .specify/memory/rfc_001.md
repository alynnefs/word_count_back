# RFC-001 — Adequação do word_count_back ao Projeto B

Autora: Alynne · Status: Rascunho · Data: 09/11/2026 · Prazo de entrega: 13/11/2026

## 1. Resumo

Esta RFC lista tudo o que precisa ser modificado ou criado no repositório `alynnefs/word_count_back` para cumprir o Projeto B (nível simples) do Módulo 4. Cada ponto tem identificador, arquivo afetado e critério de aceite, para servir de checklist de execução.

## 2. Contexto

- **Rubrica (igual para A e B):** M1 funciona, código e design (35); M2 testes e CI verde (20); M3 ambientes, segredos e observabilidade (15); M4 arquitetura, documentação e desempenho (30).
- **Critério geral:** engenharia, não tamanho. Um B impecável vale mais que um A pela metade.
- **Prazos:** entrega oficial no Moodle até 13/11; apresentação opcional ao vivo em 16/11 (ou vídeo até 13/11), com bônus de até 10 pontos. Commits depois de 13/11 não são avaliados.
- **Base escolhida:** `word_count_back`, uma API Flask com Dockerfile, pytest, coverage e CI no Travis. O `word_count_front` (Vue) entra só como apoio à demonstração.

## 4. Objetivos e não objetivos

**Objetivos**

- Cobrir todos os entregáveis do Projeto B e todos os itens de entrega do Moodle.
- Ter CI verde e README que permite subir a aplicação em ambiente limpo.
- Dar à API pelo menos uma decisão técnica real para defender no ADR e na apresentação.

**Não objetivos**

- Migrar para o Projeto A ou decompor em módulos.
- Adicionar banco de dados ou autenticação.
- Incluir o front no CI, nos testes ou na cobertura.
- Refatorar o front.

- **Remover o GET imediatamente:** simplifica a API, mas quebra o front sem necessidade. Descartada em favor de depreciar.

## Apêndice A: rascunho do ADR 0001

**Título:** receber o texto no corpo de uma requisição POST.

**Contexto:** o endpoint atual recebe o texto na URL (`GET /count/<texto>`). URLs têm limite de tamanho, exigem codificação de espaços e caracteres especiais, e o texto acaba registrado em logs de acesso.

**Opções:** (1) manter GET com o texto na URL; (2) `POST /count` com corpo JSON.

**Decisão:** adotar o POST com corpo JSON, mantendo o GET como depreciado por compatibilidade com o front.

**Consequências:** textos longos passam a funcionar; é possível validar o tamanho e responder 413; o front precisará migrar para o POST depois; o OpenAPI precisa documentar os dois endpoints e marcar o GET como depreciado.
